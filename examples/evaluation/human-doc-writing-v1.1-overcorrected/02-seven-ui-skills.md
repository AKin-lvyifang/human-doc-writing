# 七个 UI Skills 装好以后，先让用户找到总入口

这次我们安装了七个开源 UI Skills。用户在 Codex 里输入 `$`，候选列表里出现七个以 `Better` 开头的选项。它们都和界面评审有关，名称又很接近。评审还没有开始，用户先要判断该选择哪一个，也很难从 `$better-interface full` 猜出每个词会带来什么结果。

七个工具原本有清楚的分工。六个专项分别处理 accessibility、layout、writing、typography、colors 和 UI polish，也就是无障碍、布局、界面文案、字体排版、颜色和整体精修。`better-interface` 负责完整评审，也会协调这六个专项。

这层关系在选项列表里没有显示出来。七个名字并排出现以后，总入口和专项入口处在同一层。工具作者知道每个 Skill 负责什么，第一次使用的人只看到七个都能检查界面的选项。内部已经分好的职责，没有变成用户可以直接理解的选择。

日常使用只需要从 `Better Interface` 开始。用户写清要评审的对象，再说明这次检查的边界，总入口就能调用合适的专项并整理结果。一个设置页、一段已有界面或某条操作流程都可以成为评审对象。边界则负责说明哪些状态、页面和交互需要包含在本轮检查里。

用户不需要先把问题分成布局、颜色或文案，也不需要把七个 Skill 逐个调用。同一个评审对象可能涉及多个领域，总入口负责判断需要哪些专项，再把各项结果整理回来。用户只负责说明要检查的页面、流程和已有状态。

调用里的 `full` 表示完整评审。它会覆盖六个领域，也会查看已经存在的错误状态、空状态和窄窗口表现，最多报告十五个问题。这个模式适合准备做一轮完整检查时使用。范围更广，返回的问题也更多，用户需要为后续处理留出时间。

`quick` 表示快速评审。它只检查主路径上的高、中优先级问题，最多报告五个。用户需要先找出当前页面最影响使用的地方时，可以选择这个模式。两个模式承担不同的检查范围，入口说明需要把这种差别直接写出来。

评审默认只读，这一点也应出现在入口附近。Skill 会指出问题并提出改进意见，不会自动修改代码。用户可以先查看报告，再决定是否实施改动。需要修改代码时，再单独提出范围和要求。

这次困惑同时涉及发现性和用户对工具关系的理解。发现性决定用户能否找到开始评审的位置。产品设计里常说的心智模型，则描述用户怎样理解总入口、专项工具和参数之间的关系。七个名字能够被看见，只解决了找到工具的问题，入口关系和执行结果仍要解释。

安装提示可以先介绍 `Better Interface`，再说明六个专项由它协调。选项列表也可以给总入口加上明确说明，让它和专项检查在名称旁就能区分。随后用普通话解释 `full`、`quick` 和只读边界，用户第一次调用前便能知道该做哪些选择。

六个专项仍然值得保留。熟悉工具的人可以按需单独调用，完整评审也需要它们各自提供专业检查。面向第一次使用的人，界面只需要把第一步说清楚，把后面的调度留给总入口处理。

一段足够实用的首次提示可以直接写明，日常界面评审请选择 `Better Interface`，填写评审对象和边界；完整检查使用 `full`，快速检查使用 `quick`；评审只报告问题，不会自动修改代码。用户读完这几句，就可以开始评审，不必先研究七个工具的组织方式。
