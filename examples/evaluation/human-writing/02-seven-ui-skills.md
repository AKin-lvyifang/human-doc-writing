# 七个 UI Skills 装好以后，先把总入口说清楚

这次我们装了一组开源 UI Skills，一共七个。用户在 Codex 里输入 `$`，眼前出现七个以 `Better` 开头的选项。它们看上去都和界面有关，名字也都像能解决问题。接下来该选哪个，反倒成了第一个问题。

七个工具各有分工。其中六个专项分别处理 accessibility、layout、writing、typography、colors 和 UI polish。换成普通话，就是无障碍、布局、界面文案、字体排版、颜色和整体精修。剩下的 `better-interface` 负责总评审，也会协调另外六个专项。

设计这套工具的人已经安排了入口，可用户未必能从七个并列选项里看出来。列表把它们摆在同一层，视觉上没有主次。一个普通用户很自然地会想，我要先做布局检查，再做颜色检查吗，文案和无障碍要不要另跑一次。能力越完整，选择反而越费力。

正确用法其实很短。选择 `Better Interface`，再写清要评审的对象和边界就够了。总入口会根据任务调用六个专项，用户不需要把七个 Skill 逐个点一遍。这个关系如果没有提前讲明，安装成功只代表工具已经到了，离顺利用起来还差一步。

`$better-interface full` 更容易暴露这个问题。熟悉命令的人也许会把 `full` 理解成一个模式，第一次接触的人看到的只是两个陌生词。他不知道前一个词负责调度，也不知道后一个词会改变评审范围。这条指令由两个明确的词组成，使用者心里仍然没有对应的动作。

在这套 Skill 里，`full` 表示完整评审。它会覆盖六个领域，也会查看已有的错误状态、空状态和窄窗口表现，最多报告十五个问题。它适合准备进行一轮较完整的界面检查时使用。范围更广，输出也更多，用户要留出处理问题的时间。

`quick` 表示快速评审。它只看主路径上的高、中优先级问题，最多报告五个。用户想先知道当前页面最该修什么，或者只想在有限时间里抓住明显问题，用这个模式就够了。两个词的差别没有多复杂，用户只要知道它们各自对应什么选择。

还有一件事必须在入口处说清。这类评审默认只读，它会找问题并给出意见，不会自动修改代码。若用户以为调用之后界面会直接变化，等结果出来就会产生新的困惑。工具做了它承诺的事，用户却以为它没有生效。职责边界晚说一步，体验就会多绕一圈。

所以这次遇到的是发现性和用户理解方式的问题，产品设计里也常把后者叫作心智模型。发现性关心用户能否找到该用的入口。用户理解方式关心他能否看懂入口、专项和参数之间的关系。七个名字出现在列表里，只解决了“看得见”。哪个是总入口，由谁调度其余工具，每个词会改变什么，还需要一段清楚的说明。

这样的说明甚至不必很长。可以直接告诉用户，日常评审请选择 `Better Interface`，写上评审对象和边界。想全面检查就用 `full`，只想先抓主路径问题就用 `quick`。评审默认只读，如需修改代码，要另外提出实施要求。读完这几句，七个选项才会在脑子里排好位置。

安装后的提示也可以先介绍总入口，再说明六个专项由它协调。选项列表若能给 `Better Interface` 标出总评审身份，用户就不用从相似名字中猜层级。随后再解释 `full`、`quick` 和只读边界，整套工具的关系就能在第一次使用前讲明白。

工具设计很容易把精力放在能力清单上。多一个专项，就多覆盖一类问题。这当然有用。普通用户此刻只是在输入框里准备完成一件事，很少会先研究一张能力架构图。他需要知道第一步点哪里，后面的调度由谁负责，结果会做到哪里为止。

一个好入口会把复杂性留在工具内部，同时把必要的选择交给用户。对象和边界需要用户决定，六个专项怎样协作可以由总入口处理，评审模式则用清楚的普通话解释。这样一来，七个 Skills 才会成为一套工具。否则，它们只是七个都很有用、却让人不知道先点谁的名字。
