# 七个 UI Skills 摆在眼前，我只想知道该点哪一个

这次装完七个开源 UI Skills，用户在 Codex 里输入了一个 `$`。候选列表随即展开，七个选项都以 `Better` 开头。

然后问题来了，该选哪一个？

从工具作者的角度看，七个名字各自清楚。六个专项分别处理 accessibility、layout、writing、typography、colors 和 UI polish。换成普通话，它们关注无障碍、页面布局、界面文案、字体排版、颜色使用和界面精修。每个领域都有自己的检查重点，拆开很合理。

可用户看到的并不是这套分工。他看到七个相似入口，需要在还没开始评审之前，先理解每个 Skill 的职责。列表里还有一个 `Better Interface`，旁边的调用方式写着 `$better-interface full`。如果没人解释，用户既不知道它和另外六个是什么关系，也不知道 `full` 会触发什么。

工具数量在这一刻成了表象。造成困惑的是入口没有把职责关系说出来。

这七个 Skills 其实已经有总入口。`better-interface` 负责完整的界面评审，并协调另外六个专项。用户无需逐个调用七次，也无需先判断自己的问题到底属于布局、颜色还是文案。正确的开始方式只有一步，选择 `Better Interface`，再写清要评审的对象和边界。

对象告诉工具要看什么，可能是一个页面、一段已有界面或某个明确范围。边界告诉它哪些内容在这次检查之内。用户做完这两件事，总入口便可以把问题交给合适的专项，再把结果整理回来。

这样设计的价值，在一处界面同时出现多类问题时会显出来。一个按钮难以辨认，可能和颜色有关，也可能涉及文字表达与无障碍。页面在窄窗口里拥挤，又会牵动布局和字体。让用户先给问题分类，相当于要求他在获得评审之前先学会评审。总入口存在，就是为了接下这一步判断。

调用中的 `full` 也需要翻译成人能预期的结果。它表示完整评审，会覆盖六个领域，也会检查已有的错误状态、空状态和窄窗口表现，最多报告十五个问题。这里的上限很重要。完整不意味着把发现的每个细节都倒给用户，它仍然要控制结果规模，让一轮评审可以被消化。

如果只想快速扫一遍主路径，可以使用 `quick`。它只看主路径上的高、中优先级问题，最多报告五个。时间紧，或产品仍在早期调整时，这个模式能先把最影响使用的地方挑出来。等主要问题处理完，再决定是否需要完整评审。

无论选择 `full` 还是 `quick`，评审默认只读。它会指出问题，不会自动修改代码。这个默认行为也应该在入口附近讲清楚，因为“运行一个 UI Skill”很容易让人担心它会直接改动现有页面。知道它先看、先报，用户才敢在真实项目里调用。

回头看这次安装，七个工具本身并没有互相冲突。六个专项提供检查能力，一个总入口负责调度。问题出现在它们抵达用户眼前的那一步。相似的名字并排出现，层级关系被压平了，内部清楚的分工没有变成外部清楚的选择。

这也是发现性和心智模型的问题。发现性决定用户能否一眼找到起点，心智模型决定他能否理解工具接下来怎样工作。一个入口若只给出命令，没有说明“谁负责总评审”“其余工具由谁调用”“每个参数会改变什么”，用户仍然要靠猜。

能力越多，入口越要克制。专项可以继续保留，因为它们承担不同职责，也允许熟悉工具的人按需单独使用。面向第一次调用的人，界面只需清楚地告诉他，先选 `Better Interface`，写下评审对象和边界，再在完整检查与快速检查之间做一个选择。

七个 Skills 没有必要缩成一个 Skill。它们需要的是一个不会让人选错起点的入口。
