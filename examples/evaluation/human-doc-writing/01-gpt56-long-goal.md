# 一整晚还在 Phase 0，长任务需要一个明确的出口

我们最近在 Codex 里用 GPT-5.6 处理长任务和 Goal 任务，碰到过一个很有意思的情况。任务从 Phase 0 开始跑，整整一晚都没有停。第二天再看，它依然待在 Phase 0。

翻回执行过程，很难说它偷懒了。它一直在检查假设，补测试，寻找新风险，也一直在证明眼前这套方案够不够正确。每解决一个问题，它又能发现另一个问题。有些属于后面的开发阶段，有些属于生产环境加固，还有些只是以后可能需要的能力。它把这些问题继续放进当前范围，Phase 0 便越做越大。

执行过程一直有动作，也有结果，只是这些结果没有把它推到下一阶段。尤其当测试已经不再提供新证据时，它仍可能换一种方式复查。原来的判断没有变化，真实失败也没有增加，执行却还在继续。时间花出去了，开发阶段迟迟没有开始。

先把边界说清楚。这是我们在特定长任务工作流里看到的倾向，不能据此断言 GPT-5.6 做所有任务都会如此。深度推理在复杂工作中很有价值。它会主动寻找遗漏，也愿意追到证据足够为止。麻烦出在任务只给了一个很远的终点，却没有写明当前阶段怎样才算结束。模型越认真，越容易把“还能检查什么”当成“现在必须完成什么”。

解决办法要落到任务说明里。当前 Goal 要回答这次究竟要得到什么，当前 Phase 要限定眼下只做哪一段，交付物要让结果能够被看见，验收标准则要告诉执行者什么时候可以离开。四件事写清以后，新发现的问题才有地方可放。

判断一个问题要不要进入当前行动，可以问它是否直接影响当前交付，是否对应一个真实失败，或者是否已经构成直接阻塞。三个条件都不满足，它就不该在这一轮继续扩张。未来阶段的工作可以记录，生产级加固可以进入后续计划，可选能力也可以留在待办里。记录它们不等于现在实现它们。

测试也需要同样的边界。开发过程中，先跑受影响的最小检查。改了一个局部行为，就验证这个行为及其直接依赖。全量回归留到阶段集成、最终交付，或者公共契约和高风险行为发生变化的时候。质量要求仍然保留，每次验证也能对应一个具体问题，失败会更容易定位。

停止条件也要写进任务。验证如果已经不再产生新证据，就停止扩展测试。这里的新证据很具体，可以是新的失败、被推翻的假设，或者会改变实现选择的结果。只是换个角度得到同一个结论，不能继续为当前阶段增加工作量。

停下扩展以后，任务只剩两条路。存在真实阻塞，就转入根因诊断，弄清失败从哪里来。没有真实阻塞，就按验收标准结束这一阶段，进入下一阶段。这个分流看起来朴素，却能防止“再确认一次”变成没有尽头的执行方式。

“跑完”和“不要停”也需要放回正确位置。它们要求执行者持续完成当前目标，遇到困难别提前退出。它们没有授予扩大目标的权限。若把“不停”理解成把所有未来风险都提前解决，再长的夜也不够用，因为任何复杂系统都能继续找到下一件值得担心的事。

下一次写长任务，可以把出口直接放进提示里。当前阶段的交付物满足约定验收，受影响的最小检查已经通过，验证没有提供新证据，也不存在真实阻塞，此时就进入下一阶段。只要其中一项没有满足，执行者也能指出缺的是什么，不必靠继续复查来证明自己仍在工作。

长任务需要耐心和深度推理，也需要这道能被执行的阶段出口。到了出口，交付已经满足，检查已经给不出新东西，阻塞也不存在，那就往前走。能发现问题是一种能力，知道哪些问题该留给下一阶段，同样是一种能力。
