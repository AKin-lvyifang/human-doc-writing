# 写作画像外面，为什么还要加一道统一门禁

这次整理写作工具时，我们把旧的 `khazix-writer` 移进了废纸篓。它一共有 414 行，文件仍可恢复。

旧 Skill 的辨识度很高。它围绕“数字生命卡兹克”这个固定人设写公众号，会自动匹配公众号任务，也带着作者身份、口癖和固定尾部。只要目标是复现这一位作者，它能给出很明确的方向。可当写作对象从公众号扩展到产品文档、教程、PRD、README 和小红书，固定人设就会进入每个不该由它决定的场景。

与此同时，最新开源 `human-writing` 已经到了 1.0.0。它处理的是通用中文创作与改稿，不要求模仿卡兹克本人。它先检查现实稿的材料够不够，再处理作者从什么位置说话、段落有没有往前走、中文词序是否自然，随后完成七遍改稿和自动检查。

这套规则有一个很明确的边界。它不建立作者画像，也不维护个人规则库。

我们自己的 `human-doc-writing` 正好从另一端出发。它把渐进式画像放在中心，按文章类型选择不同写法。用户认可一篇文章，可以把其中可迁移的写作决策保存下来。用户反感某种写法，也可以留下避坑画像。公众号、产品文档、教程、PRD、README 和小红书各走自己的类型路由，不必共享同一套开头、节奏和收尾。

两套能力解决的并不是同一道题。画像回答的是“在这个场景里，我倾向于怎样写”。通用中文检查回答的是“无论写哪一种文体，哪些问题都不该出现”。少了前者，文章可能干净，却不像用户长期形成的表达。少了后者，画像越丰富，越可能把共同的模型化问题一起保存并重复。

一个公众号画像可以偏爱从具体经历进入，让读者跟着一次发现过程往前走。教程需要更明确的步骤和验证结果，PRD 需要让团队形成可执行的决定，README 则要帮助访客判断项目并跑起来。这些差异值得保留。若用一道人味规则把所有文体压成同一种散文，场景需要的信息结构就会丢失。

但不同文体也会掉进相似的坑。现实稿可能用没有来源的细节装出现场感，段落可能只是换词重复上一段，判断前面可能摆着模型常用的路标，普通事情可能被商业黑话抬得很高，结尾可能在内容讲完后继续总结和升华。换了文章类型，这些问题仍然存在。

最后采用的融合方案，是保留 `human-doc-writing` 已有的画像、类型卡、确认卡和长文编排，再让所有成稿经过同一道人味终审。画像继续决定开头、推进、详略、格式与收尾，统一终审负责核对事实和材料，检查每一段有没有增加新信息，也会清理假具体、模型路标、商业黑话与机械结尾。

这个顺序很关键。先有场景，再过公共检查。终审不替公众号决定该用什么语气，也不替 PRD 决定模块怎样组织。它只阻止一种情况发生，某个写法因为被画像记录下来，就自动获得长期通行证。用户偏好仍然有效，事实边界与材料要求拥有更高优先级。

社媒中长文会使用更严格的散文检查。公众号、小红书和其他长文里的套式转折、夸张路标、空洞黑话与机械收束，都要被单独清理。README、PRD 和教程则保留必要的冒号、列表、表格、代码和准确术语，因为这些格式承担导航、对比和执行任务。保留格式不等于允许空话躲在格式后面，列表里的每一项仍要带来事实、动作或规则。

融合之后，最新版 `human-writing` 也没有消失。它仍作为独立 Skill 安装，用户想要通用中文创作或改稿时，可以显式调用。融合版继续服务个人画像与跨场景写作。一个提供独立通用能力，一个把通用门禁接进已有的个人写作系统，使用位置各自清楚。

把旧 Skill 移进废纸篓，也没有否定人设型写作。它只是让固定作者身份回到适合它的范围。个人写作系统要长期使用，靠的不能只有“像谁”，还要知道这次写什么、材料够不够、每一段是否真有东西可说。

画像让文字因人因地变化，统一门禁守住所有文章都不能越过的线。两者放在一起，个人风格才不会变成另一种自动生成的模板。
