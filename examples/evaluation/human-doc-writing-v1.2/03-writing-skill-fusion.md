# 我们把 human-writing 融进个人写作 Skill 后，改了哪几步

这次整理本机写作工具，我们先把旧的 `khazix-writer` 移进了废纸篓。它一共有 414 行，围绕“数字生命卡兹克”的固定人设写公众号，会自动匹配公众号任务，也会把作者身份、口癖和尾部带进成稿。文件仍然可以恢复，只是离开了默认入口。它适合复现一个固定人设，拿来覆盖公众号、README、PRD 和教程，口气很容易跟着跑错地方。

接着安装的是开源 `human-writing` 1.1.0。它面向通用中文创作和改稿，不要求模仿卡兹克本人。现实长稿动笔前，它会先检查材料能否托住目标篇幅，计划写到约 1,200 字时要找出至少五件能组成实际过程的材料。随后再确定谁在说、他凭什么知道，让段落沿事实和动作往前走，初稿完成后才做七遍修改和自动检查。它把一篇文章写顺，却明确不建立作者画像，也不维护个人规则库。

我们原来的 `human-doc-writing` 已经在做另一件长期工作。它会先判断文章类型，再读取这个类型下当前有效的正向画像和避坑画像。用户认可一种开头、信息顺序或收尾方式，可以把写作选择留下来；用户指出反问、自问自答和整齐列表很像 AI，也能让以后同类文章绕开。公众号、小红书、产品文档和 README 因此不会被压成同一种口吻。两套工具放在一起以后，我们保留了类型路由、画像、确认卡和长文编排，也把 `human-writing` 的材料检查、普通白话推进和初稿后修改接了进来。固定人设没有跟着迁移，示范里的句子和故事也没有进入个人画像。我们吸收的是写作时怎样判断材料、怎样把事情讲下去，以及成稿后怎样拆掉模型摆出来的姿势。

现在一篇公众号稿开始前，系统先核对事实和材料。目标有明确下界时，写前会留一张材料覆盖表，把必须保留的动作、限制、失败和后果记下来。材料够了，再读取公众号画像和正向起稿规则，沿实际发生的过程写第一稿。详细禁令留到全文已经成形以后，不在第一段落笔前一起压上来。

这个顺序来自一次很具体的失败。前一轮融合把终审规则读得太早，模型从开头就忙着躲避风险。结果并不好。三篇稿子最后都写成了 12 段，文字安全、整齐，读起来却像产品说明。第二篇只剩 1047 个汉字，删掉模型腔时，帮助理解的过程和后果也被一并删了。检查项变少了，文章没有因此更自然。

独立版给出的修正很直接。第一稿先跟着眼前材料走，复杂的地方可以多说几句，已经讲明白的地方很快过去。作者可以补充，也可以承认前面一句不够准，只要这些岔路确实带回新信息。段落不预设数量，多个议题也不共用同一副骨架。判断从事实附近长出来，普通地方就用普通句子结束。

完整初稿写完以后，人味终审才进场。它先保护稿子里已经成立的材料来路、普通判断和不规则节奏，再清掉假问题、点题金句、无来源细节、商业黑话和机械总结。删改完成后还要回看材料覆盖表。必须保留的过程若消失了，就从原材料补回来；总字数低于约定下界也不能直接交付。三篇以上一起写时，再比较段落数和推进位置，防止换了主题却仍然长成同一篇文章。

不同文体仍然按自己的方式工作。公众号沿事实和判断连续读下去，现有个人画像还要求现实稿不用问号，也不靠孤立短句制造余味。README、PRD 和教程需要帮助读者查找和执行，冒号、列表、表格、代码与准确术语都可以保留。终审只检查这些格式有没有承担真实信息，不会为了统一人味把技术文档改成散文。

独立的 `human-writing` 1.1.0 继续安装在本机，需要通用中文创作时可以直接调用。`human-doc-writing` 用在需要个人画像、类型路由和跨场景积累的任务里。旧的 `khazix-writer` 还在废纸篓，固定人设随时能够恢复，但它已经不再替所有公众号文章决定作者是谁。
