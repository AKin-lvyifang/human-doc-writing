# 七个 UI Skills 装好以后，需要先认准一个入口

这次安装的开源 UI Skills 一共有七个，用户在 Codex 里输入 `$`，眼前会同时出现七个以 `Better` 开头的选项。能力都已经装好了，选择却从这里变得困难。每个名字看起来都和界面有关，用户不知道应该点哪一个，也看不懂 `$better-interface full` 里的 `full` 到底会触发什么，工具已经进入选择列表，第一次评审却卡在了选择入口这一步。

七个 Skill 并不要求用户轮流走七套流程。其中六个是专项工具，分别处理 accessibility、layout、writing、typography、colors 和 UI polish，也就是无障碍、布局、界面文案、字体排版、颜色和细节打磨；`better-interface` 是总评审入口，它会根据一次评审的需要协调另外六个专项。从工具内部看，这种分工很清楚，专项各自守住一个领域，总入口负责把结果放回同一次界面评审。到了用户面前，内部结构却被平铺成七个同级选项。用户只看到七个都能调用的名字，看不到一个入口和六个由它调度的能力。工具数量因而显得很多，影响使用的职责关系又没有被看见。

正确的使用动作其实很短。用户只需要选择 `Better Interface`，接着写明要评审的对象和边界，不必把七个 Skill 逐个调用。总入口接到任务后，再去协调六个专项。用户要做的是描述这次评审，不是替工具安排内部调度。入口关系写清后，用户的注意力就能回到评审对象和边界，不必先研究六个专项的调用顺序。少了这层说明，“已经安装七种能力”很容易被理解成“开始前要先决定调用哪一种能力”，还没进入评审，操作负担就已经出现了。

`full` 和 `quick` 也不是额外的 Skill，它们是同一个入口下的两种评审范围。`full` 表示完整评审，会覆盖六个领域，并把错误状态、空状态、窄窗口等已经存在的界面状态放进同一次检查，最多报告 15 个问题。用户写下 `full`，是在要求一次覆盖更完整、报告上限更高的评审。

`quick` 表示快速评审，只检查主路径上的高、中优先级问题，最多报告 5 个。它沿用同一套评审逻辑，把注意力收在最影响当前使用的部分。六个专项没有因此变成六次单独调用，返回内容只是收得更紧。用户在这里选择的是本次评审要看多深、返回多少内容，无需再挑一个专项。一个模式看得更全，一个模式先集中处理主路径上的重要问题，差别落在评审范围和问题数量上。

两种模式默认都是只读，Skill 会检查并报告问题，不会自动修改代码。这条信息让入口的边界也变得清楚。“开始评审”和“授权改动”是两件事，用户选中总入口并写下对象、边界和模式，只是在决定看哪里、看多深，不等于把代码修改权一并交出去。知道这一点后，`full` 的完整指向评审覆盖面，不会被误解成自动完成一轮代码修改。

这样再看 `$better-interface full`，每个词才有明确位置。`$better-interface` 指向总入口，`full` 决定评审范围，后面的文字说明对象和边界。命令本身并不复杂，第一次看到它的用户缺少的是这三个部分各自做什么的解释。入口、模式和任务描述一旦接上，七个 Skill 就不再要求用户先学会一套内部组织方式。

这次困惑暴露的是发现性和心智模型问题。发现性决定用户能不能从一排名称里认出应该从哪里开始；心智模型决定他能不能理解总入口会调度哪些工具、模式词会怎样改变结果。只展示全部能力，却不展示它们之间的关系，能力越多，首次使用时越像一道选择题。用户需要记住的应该是一个入口和两种范围，其余专项由总入口在评审过程中协调。

安装七个 UI Skills 之后，用户需要一条稳定路径。选择 `Better Interface`，写明评审对象和边界，需要完整覆盖时使用 `full`，只想先看主路径上的重要问题时使用 `quick`。评审默认只读，结果不会自动变成代码修改。其余六个专项留在总入口之后工作，七种能力就能汇入一次容易开始的评审。
