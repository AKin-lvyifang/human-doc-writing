# 中文自然写作

这项 Skill 处理两类任务：

1. **画像灌输**：从用户认可或反感的文章中，提炼可复用的写作决策。
2. **按画像写作**：识别文章类型和文档形态，读取对应画像，再新写、重写或编辑。

画像记录开头、信息推进、详略、段落节奏、格式选择和收尾方式。画像不提供事实，也不是固定栏目模板。所有画像和类型卡都服从同一道人味终审；画像决定怎样表达，终审保证材料站得住、文章真在推进，也没有用模型腔假装真人。

类型卡、画像、参考协议和脚本都保存在本 Skill 内。项目材料只用于确认事实、术语、能力边界和发布条件。

## 0. 先判断工作模式

### 进入画像灌输模式

用户出现以下意图时，不要直接写新文章：

- “这是一篇很棒的说明文，学习它。”
- “把这个 Markdown 灌输成公众号文章画像。”
- “记住这个 README 的写法。”
- “提炼这个链接的写作风格。”
- “这是典型 AI 体，把它作为反例。”
- “用这篇替换当前的小红书画像。”

### 进入写作模式

用户要求新写、重写、扩写、压缩、润色、结构调整、拆分、检查或清理 AI 体时，进入写作模式。

同一条请求既要求灌输又要求写作时，先完成灌输，再使用新画像执行写作。

# A. 画像灌输模式

## A1. 读取来源

可接受：

- 用户附加的 Markdown、TXT、DOCX、PDF 或其他可读文档。
- 用户粘贴的正文。
- Codex 当前能够完整访问的网页链接。

若链接需要登录、验证码、订阅或正文无法完整读取，不根据标题和摘要猜测。请用户改为提供正文或文件。

## A2. 确定文章类型

读取 `references/type-router.md`。

优先级：

1. 用户明确说的类型。
2. 文件名、发布平台和文章用途。
3. Skill 识别出的子类型。

用户指定主类型时，不擅自改成别的主类型；明显不匹配时只提醒一句。

## A3. 提炼画像

读取 `references/portrait-ingestion.md`。

必须做到：

- 一篇文章即可建立一个当前画像，不要求用户补交样文。
- 提炼可迁移的写作决策，不复述主题内容。
- 区分稳定写法和只属于该篇文章的偶然习惯。
- 不保存整篇原文，不复制标志性句子、标题、比喻、故事或结论。
- 不要求用户填写 YAML、frontmatter 或元数据表。

正向样文保存为“参考画像”；反例保存为“避坑画像”。

## A4. 保存画像

画像使用普通 Markdown，格式参考 `references/portrait-template.md`。

默认路径：

- 正向画像：`user/portraits/<type_id>.md`
- 反例画像：`user/anti-patterns/<type_id>.md`
- 历史版本：`user/history/`

优先调用 `scripts/portrait_store.py` 保存。先检测当前系统可用的 Python 命令。

默认行为：

- 同类型已有画像时，先自动备份旧版。
- 新画像成为该类型当前默认画像。
- 除非用户明确要求，不把多篇文章平均混合。

脚本无法运行时可以手动完成同等文件操作，但不能静默覆盖旧画像。

## A5. 灌输完成后的回复

只给简短结果：

```text
已建立：说明文画像（机制解释型）
来源：article.md
以后写说明文时默认采用：
- 从具体问题直接切入
- 先讲因果，再给定义
- 段落连续推进，少用整齐列表
- 结尾停在边界或行动，不重复总结

已排除：文章事实、独有观点、标志性表达。
旧画像：已备份 / 原来没有。
```

除非用户要求查看，不贴出完整画像全文。

# B. 写作模式

## B1. 先读取事实

在不修改目标文件的前提下读取：

- 用户请求、原文、目标文件和用户指定材料。
- 与任务相关的 README、CHANGELOG、配置、测试、代码入口和已批准文档。
- 已有产品用词、能力边界、品牌限制和发布条件。

能从材料确认的事实直接使用。无法确认且会改变结论的事实才向用户提问。

随后读取 `references/human-voice-gate.md` 的“事实与材料门”。先区分现实、虚构或混合写作，再确认内容靠什么站住。非虚构中长文不能把推理、同义改写、假设人物或装饰细节算成新材料。

公众号、知乎、博客和社媒非虚构长文计划达到 1,200 字时，内部至少列出五件能组成实际过程的具体材料，并记清来源。材料不足时按顺序处理：可公开研究就先研究；需要用户经历就一次问完最多三个问题；用户要求直接出稿且无法补充时缩小题目并缩短篇幅。不要用重复解释补齐目标字数。

## B2. 建立文档契约

读取 `references/type-router.md`，确定：

- 主类型和必要的子类型。
- **统领目标**：这篇内容最终帮读者完成什么。
- 主要读者、次要读者和阅读场景。
- 必须覆盖的内容模块、明确不覆盖的范围。
- 文档形态：连续叙事、模块化长文，或多交付物。
- 事实标准、术语和输出位置。

主类型用于选择画像，不限制文章只能谈一个方面。

一篇长文可以包含多个主题、机制、案例和用途，只要它们共同服务同一个统领目标，并能由一套清楚的信息架构串起来。不要因为标题多或篇幅长就自动拆分。

出现以下情况时，才优先拆成多个交付物或正文加独立附录：

- 主要读者明显不同。
- 阅读时机不同，例如首次了解、操作查询和版本迁移。
- 内容更新频率或维护责任不同。
- 事实来源、权限或公开范围不同。
- 各部分需要完全不同的表达方式，合在一起会互相妨碍。

## B3. 读取当前画像

按以下顺序读取：

1. `user/portraits/<type_id>.md`，存在就作为主要写作依据。
2. `user/anti-patterns/<type_id>.md`，存在就作为避坑依据。
3. 没有正向画像时，才读取 `references/types/<type_id>.md` 作为初始化规则。

画像负责结构、节奏和取舍，项目材料负责事实。用户本次明确要求高于画像。

画像与 `references/human-voice-gate.md` 冲突时，事实边界、材料门和禁止伪造优先。不得为了复现画像中的“场景感”“人物感”或“活人感”补写用户没有提供、来源无法核验的经历、人物、对白、心理和精确细节。

## B4. 选择执行方式

当任务是长文、多来源或多模块时，读取 `references/long-form-orchestration.md`。

先在以下方式中选择：

1. **单 Agent 完成**：短文、紧密叙事、资料较少或协调成本高。
2. **主 Agent + 子智能体**：有多个可独立核对的来源域、事实域或内容模块。
3. **多交付物编排**：读者、使用场景或更新方式明显不同，需要多个文件。

不要按二级标题机械地“一节一个子智能体”。主 Agent 始终拥有文档契约、结构、术语、叙事主线和最终文本。

如果当前环境不能使用子智能体，就按同样角色顺序执行多个独立分析轮次，不降低最终整合标准。

## B5. 第一轮发简短确认卡

读取 `references/brief-template.md`。

除非用户明确说“直接执行”“跳过确认”，或任务只是改单句，否则第一轮不写正文、不修改文件。

确认卡必须已经预填，最多问 3 个真正影响结果的问题。不要让用户填写表格，不展示内部路径、`type_id` 或脚本名。

## B6. 用户确认后执行

- 以最后一版文档契约和确认卡为范围。
- 项目事实与画像冲突时，事实优先。
- 不复制画像来源里的句子、观点、案例和标志性表达。
- 用户改变读者、平台或交付物时，重新判断文档形态。

使用子智能体时：

- 主 Agent 先给每个子智能体边界清楚的任务和返回格式。
- 默认让子智能体做资料梳理、事实核对、模块简报、反方审查和一致性检查。
- 连续叙事型文章默认由主 Agent 写全部正文。
- 模块化长文可让子智能体提供分模块草稿，但主 Agent 必须统一重写、补过渡、消除重复和冲突。
- 只有主 Agent 修改最终目标文件；不要让多个子智能体并发写同一文件。
- 等待所有结果，解决矛盾后再成稿。不得把各段直接拼接后交付。

## B7. 独立编辑

初稿完成后，脱离原结构再编辑一次：

1. 检查统领目标、文档形态和模块层级是否一致。
2. 删除文档自述、写作预告和重复事实。
3. 统一术语、状态口径、时态和读者称呼。
4. 按当前画像调整开头、推进方式、段落节奏和收尾。
5. 按避坑画像删除对应坏习惯。
6. 检查跨模块跳跃、重复、矛盾和缺失过渡。
7. 核对事实、能力状态、来源和不确定性。
8. 在不损失事实的前提下压缩冗余。

初稿完成后读取 `references/human-voice-gate.md`，按其中的统一终审顺序再编辑一遍。所有类型都必须通过通用终审；公众号、小红书、知乎、博客和社媒中长文还必须通过“社媒中长文严格档”。技术文档保留必要的标题、列表、表格、冒号、代码、链接与精确术语，但不能用这些格式掩盖重复、空话或栏目堆叠。

最后读取 `references/editor-checklist.md`。

Markdown 或纯文本成稿必须运行 Skill 内的 `scripts/lint_ai_style.py`。公众号使用 `--profile wechat-longform --strict`；小红书、知乎、博客和其他社媒中长文使用 `--profile social-longform --strict`；其余文档使用 `--profile universal --strict`。脚本失败时先修复阻断项，再逐项判断警告。脚本只发现文字形状，不能证明文章事实可靠、真的有人味，也不能因为“标题多”就自动拆文档。

用户要求“去 AI 味”、风格改写或本地化重写，且同时有原稿和改写稿时，可运行 `scripts/de_ai_diff.py --before <原稿> --after <改写稿>` 生成前后对照。该脚本只检查改写覆盖和常见口吻词变化，不替代事实审查和人工编辑。

# C. 通用底线

- 每篇内容需要一个清楚的统领目标，但可以覆盖多个相互关联的方面。
- 结构服从读者的阅读路径，不服从固定栏目数量。
- 标题服务导航和论证，不为了形式完整而凑齐。
- 列表只用于真正并列、步骤或需要快速扫描的信息。
- 术语只解释一次，跨模块保持同一口径。
- 面向非技术读者时，术语、命令、路径、配置项首次出现要说明“做什么”和“对读者有什么用”，不要只报名词。
- 不编造经历、用户反馈、数据、案例、测试结果或社会证明。
- 不用模型临时想出的“某个人”“比如有一次”、精确天气、神态、房间摆设或对白给现实稿撑篇幅。
- 每个主要段落必须带来新事实、新动作、新例子、新区别或新后果；同一判断换一种说法不算推进。
- 读者下一步可能会问什么，只用于内部安排信息顺序。不要替读者设问，再由作者回答。公众号非虚构正文不用问号，把素材里的提问改写成不改变含义的事实、处境、理解障碍或间接引语。
- 不用一句孤立的短判断制造停顿和深意。删掉后事实、因果和动作都不变的“点题金句”直接删除；需要保留的判断并入相邻段落，用具体对象和原因说清。
- 作者可以是亲历者、业内人、调查者或资料整理者，但不能把查到的内容写成亲历，把猜测写成内幕。
- 声称“已验证”“已通过”“可发布”时，必须有已执行的命令、已读取的文件或可核验来源；脚本和检查表存在不等于已经触发。
- 成稿不得保留内部 source 注释、待核实标记、过程说明、路由指令、画像提炼痕迹或 Agent 自检语言。
- 不用“本文将”“一句话说明”“核心理念”等元话语替代内容。
- 不连续使用同一种对比句、三连口号、相同句首和机械排比。
- 不为了像人故意加入错别字、网络梗、假情绪或虚构口头禅。
- 不用宏大结尾、硬升华、首尾回环或固定互动口播替代已经讲完的内容。

# D. 画像管理

用户可以直接说：

- “查看我的说明文画像。”
- “列出现在有哪些画像。”
- “恢复说明文默认规则。”
- “删除公众号反例画像。”
- “用这篇替换当前 README 画像。”

处理这些请求时使用 `scripts/portrait_store.py`，不要要求用户进入目录手动编辑。

# E. 交付

默认只交付正文、文件修改结果或灌输结果，不附带大段写作方法说明。
