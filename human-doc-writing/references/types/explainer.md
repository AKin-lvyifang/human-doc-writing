# 类型写作卡：说明文 `explainer`

## 适用范围

适合解释一个概念、机制、规则、方法或方案。重点是让读者理解，不是推销产品，也不是带着读者逐步操作。

常见子类型：

- `concept`：概念解释。
- `mechanism`：机制或流程说明。
- `policy`：规则、政策或边界说明。
- `proposal`：方案原理说明。

## 读者结果

读完后，读者能用自己的话说明：它是什么、为什么这样、如何运作、边界在哪里。

## 写前必须确认

1. 读者已经知道什么。
2. 读者最容易误解哪一点。
3. 哪个因果链或机制必须讲清。
4. 是否需要例子、对比或图示。

## 可选结构

### 结构 A：问题到机制

真实问题或现象 → 直接答案 → 运作机制 → 具体例子 → 边界或例外。

### 结构 B：场景到原则

具体场景 → 为什么旧办法失效 → 核心原则 → 如何落地 → 适用范围。

### 结构 C：误解澄清

只在确有普遍误解时使用：常见理解 → 问题在哪里 → 更准确的解释 → 影响。不要整篇都写成“不是……而是……”。

## 开头

直接写读者遇到的现象、问题或关键事实。不要写“本文将介绍”“一句话说明”“先来理解三个概念”。

## 正文

- 先讲因果，再讲结论。
- 一个术语只解释一次。
- 抽象概念至少配一个能验证理解的例子。
- 对比只在能减少误解时出现。
- 复杂机制按真实顺序展开，不为了整齐硬拆成三步。

## 结尾

用边界、影响或下一步收束。内容已经闭合时可以直接结束，不强行总结全文。

## 语言与节奏

克制、具体、连续。段落可长可短，但每段只解决一个问题。少用口号、感叹和虚构对话。

## 常见 AI 痕迹

- 开头先定义文档定位。
- 连续写“简单来说”“换句话说”。
- 同一概念分别用定义、列表和总结重复三次。
- 所有章节都是“导语 + 三点列表 + 总结”。
- 为了显得全面，加入与读者问题无关的历史和未来展望。

## 交付检查

- [ ] 前两段已经进入真实问题或答案。
- [ ] 机制和因果关系能够被复述。
- [ ] 例子提供了新信息，不是换句话说。
- [ ] 对比句没有成为全文骨架。
- [ ] 没有把说明文写成产品宣传或操作手册。
