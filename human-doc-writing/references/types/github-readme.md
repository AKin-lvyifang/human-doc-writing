# 类型写作卡：GitHub README `github-readme`

## 适用范围

适合开源仓库或公开代码仓库首页。README 首先服务第一次到访的人，其次才服务维护者。

常见子类型：

- `library`：开发库或 SDK。
- `cli`：命令行工具。
- `app`：应用、插件或服务。
- `template`：项目模板。

## 读者结果

访客能快速判断项目是否相关，并在最短路径内安装、运行或找到深入文档。

## 写前必须确认

1. 项目是什么，解决谁的什么问题。
2. 最短可运行路径。
3. 环境、版本和兼容性。
4. 核心示例和文档入口。

## 推荐结构

1. 项目名和一句具体说明。
2. 适用场景或核心能力。
3. 截图或最小示例，可选。
4. 快速开始。
5. 常用用法。
6. 配置和兼容性。
7. 文档、贡献、许可证。

架构、路线图和完整 API 应链接出去，除非它们就是仓库的主要用途。

## 开头

第一屏回答三件事：是什么、给谁用、最快怎么试。徽章只保留有决策价值的，不把顶部装饰成机场出发屏。

## 正文

- 安装命令和示例必须来自真实项目。
- 示例优先展示最常见任务，不展示最复杂能力。
- README 作为入口，不承担完整手册。
- 对尚未支持的平台和版本明确写边界。
- 对贡献者的信息放后面或链接 `CONTRIBUTING.md`。

## 结尾

以文档入口、贡献方式、支持渠道和许可证结束。不要写宣传式总结。

## 语言与节奏

准确、可扫描、面向行动。技术术语不向专业读者过度解释，也不假设所有人熟悉项目内部名词。

## 常见 AI 痕迹

- 第一屏全是愿景，没有安装入口。
- 功能清单十几项但没有最小示例。
- “强大、灵活、现代、高性能”没有数据或事实。
- 安装、配置、架构、路线图全部堆在 README。
- 自动补出不存在的命令、环境变量和兼容性。

## 交付检查

- [ ] 第一屏能完成相关性判断。
- [ ] 快速开始可复制并与仓库一致。
- [ ] 核心示例比功能清单更突出。
- [ ] 版本、平台和权限边界准确。
- [ ] 深入内容有清晰链接。
