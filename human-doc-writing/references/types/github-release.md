# 类型写作卡：GitHub 发布说明 `github-release`

## 适用范围

适合 GitHub Release、CHANGELOG 条目和版本公告。重点是用户影响，不是把提交记录翻译成自然语言。

常见子类型：

- `major`：大版本，包含迁移和破坏性变化。
- `minor`：功能版本。
- `patch`：修复版本。

## 读者结果

用户知道这次变了什么、是否影响自己、需要做什么，以及有哪些已知问题。

## 写前必须确认

1. 版本范围和发布日期。
2. 用户可感知变化。
3. 破坏性变化和迁移步骤。
4. 修复、已知问题和兼容性。

## 推荐结构

版本主题或最重要变化 → Breaking Changes → 新功能 → 改进与修复 → 升级或迁移 → 已知问题 → 完整变更链接。

小补丁不必机械补齐所有章节。

## 正文

- 从用户结果写，不从内部类名和提交名写。
- 每项变化说明影响对象和必要动作。
- 破坏性变化放最前，并给迁移路径。
- 修复按用户场景归组，而不是逐条复制 commit。
- issue、PR 和文档链接用于追溯，不代替解释。

## 结尾

告诉用户如何升级、反馈问题或查看完整差异。没有动作时简洁结束。

## 常见 AI 痕迹

- “本次版本带来多项重磅更新”。
- 每个修复都升华成体验价值。
- 把内部重构写成用户功能。
- 遗漏破坏性变化和迁移步骤。
- 把尚未合并或路线图内容混进发布说明。

## 交付检查

- [ ] 版本和范围准确。
- [ ] 用户影响排在内部实现之前。
- [ ] 破坏性变化和迁移步骤醒目。
- [ ] 修复没有简单复制提交记录。
- [ ] 已知问题和兼容性没有被美化隐藏。
